# ADR — 아키텍처 의사결정 기록 (발표 4·5장 원천)

## ADR-1. 워크로드별 실행 환경 배치

**맥락**: 한국어 사용자를 위한 영어 일상회화 학습 서비스. 웹·WAS·DB 같은 계층이 아니라 성격이 다른 업무 기능 3개로 분해하고, 기능마다 맞는 실행 환경(VM / Container / Serverless)에 배치했다. 같은 운영 작업(배포·재배포·복구·증설)을 세 환경에서 반복해 판단의 타당성을 숫자로 확인했다(`docs/ops-matrix.md`).

**판단 기준**: 트래픽 패턴, 변경 주기, 상태 보유, 실행 시간. 기준끼리 충돌하면 같은 운영 작업을 가장 단순하게 반복할 수 있는 쪽을 선택.

| 워크로드 | 성격 | 트래픽 | 변경 주기 | 상태 | 결정 |
|---|---|---|---|---|---|
| A. content (학습 콘텐츠 관리 API) | 정합성 데이터, 관리자·조회 위주 | 낮고 일정 | 분기 단위 | RDS에 정합성 데이터 | **VM (EC2 ASG)** |
| B. chat (회화 챗봇 API) | 잦은 배포·수평 확장 | 사용자 수에 비례, 변동 큼 | 주·일 단위(프롬프트 수정) | 무상태(최근 대화 6개를 요청에 포함) | **Container (EKS)** |
| C. note (대화 기록·오답노트) | 간헐적, 학습 종료 시 몰림 | 평소 거의 없음 | 독립적인 작은 배포 | 무상태 함수 + DynamoDB | **Serverless (API GW + Lambda)** |

### 결정 A → VM
- **이유**: 정합성이 가장 중요하고 변경이 드물며 트래픽 예측이 가능. 운영자는 소수. 상시 기동과 인스턴스 단위 복구로 충분하며, 오케스트레이터를 둘 이득이 작음.
- **구성**: EC2 Auto Scaling(2AZ, 1~2대) + User Data 무인 기동(SSH 미개방, SSM만), 외부·내부 ALB.
- **감수**: 인스턴스 1대일 때 복구 중 다운타임 (실측 178.1초).

### 결정 B → Container (관리형 EKS)
- **이유**: 롤링 배포와 Pod 단위 자가 복구가 요구에 부합. Kubernetes를 직접 구성하면 컨트롤플레인 운영·업그레이드·etcd 백업·오토힐링을 맡을 전문 인력이 필요하므로, 월 $73으로 이 부담을 AWS에 맡기는 편이 총비용 면에서 유리하다고 판단.
- **구성**: replica 2 + probe, HPA 2~6(CPU 60%), Ingress ALB(target-type ip), IRSA로 Bedrock 호출.
- **감수**: 클러스터 선행 생성(약 15분)과 컨트롤플레인 상시 요금.

### 결정 C → Serverless
- **이유**: 상시 서버는 낭비이며, 호출당 과금·유휴 시 0원 구조가 적합.
- **구성**: API Gateway(HTTP) → Lambda(VPC 연결) → DynamoDB(Gateway Endpoint).
- **감수**: 콜드스타트(실측 Init 450ms)와 VPC ENI 구성.

### 공통 결정
- RDS, DynamoDB는 실행 환경이 아니라 각 기능이 함께 쓰는 **공유 저장소**.
- 이종 연동(C4): 챗봇 Pod → 내부 ALB → 콘텐츠 EC2 → RDS. 내부 ALB의 SG 소스는 EKS cluster SG ID(C8).

### 실측으로 본 결과
- 재배포: 컨테이너 27.4초 / 서버리스 20.2초 / VM 110.5초 → 자주 바뀌는 챗봇을 컨테이너에 둔 판단과 일치.
- 재배포 중 실패 응답: VM 0/108 → 잘 안 바뀌고 안정성이 중요한 콘텐츠에 VM이 적합.

## ADR-2. 버린 대안과 트레이드오프

| # | 버린 대안 | 버린 이유 | 그 대가로 포기한 것 |
|---|---|---|---|
| 1 | 챗봇을 Lambda로 | LLM 응답 지연(수 초)과 콜드스타트가 대화 경험에 그대로 드러나고, 잦은 배포 시 함수 버전 관리 부담이 큼 | 유휴 시 0원 |
| 2 | 콘텐츠 API를 컨테이너로 | 변경이 드물고 운영자가 소수라 오케스트레이터 도입 이득이 작음 | 배포 속도, 자원 밀도 |
| 3 | Kubernetes를 EC2에 직접 구성 | 컨트롤플레인 운영·업그레이드·etcd 백업·오토힐링 구현에 전문 인력이 필요하며, 인건비까지 고려하면 관리형보다 비용이 큼 | 컨트롤플레인 요금, 세부 제어권 |
| 4 | EKS 대신 ECS Fargate | 운영 부담은 가장 적으나 AWS 전용 방식이라, 이식성과 표준 생태계(Helm, HPA, 매니페스트)를 우선 | 운영 단순성 |
| 5 | NAT Gateway를 AZ마다 하나씩 | 초기 트래픽 대비 비용 효과가 작아 1개로 시작, 사용자 증가 시 이중화 예정(`docs/cost.md`) | NAT의 AZ 장애 내성 |
| 6 | 벡터 DB로 대화 주제 추적 | 주제 추적은 LLM 구조화 출력으로 충분하며, 벡터 DB 운영 비용·복잡도 대비 효과가 작음 | 장기 기억, 검색 기반 응답 |
| 7 | EKS 하나 + RDS 이중화 (초기안) | 상태·변경 주기·트래픽이 다른 기능을 한 가지 방식으로 운영하게 되어, 기능별로 적합한 환경에 나눠 배치 | 단일 기술 스택의 단순함 |
| 8 | 챗봇이 RDS를 직접 조회 | DB 크리덴셜을 두 워크로드가 나눠 갖고 스키마에 함께 묶이게 되어, 콘텐츠 API를 거쳐 읽도록 구성 | 조회 경로 한 단계(수 ms) |
| 9 | Pod에서 외부 ALB 호출 | NAT 경유 시 IP 대역으로 허용해야 하므로, 보안그룹 단위 통제를 위해 내부 ALB를 별도 구성 | ALB 한 대분 비용 |

### 요약
- 포기한 항목은 대부분 비용 또는 가용성 내성이며, 사용자 증가 시 다시 볼 결정(NAT 이중화, VM 최소 2대, 노드 증설)은 `docs/cost.md` 3장에 정리.
